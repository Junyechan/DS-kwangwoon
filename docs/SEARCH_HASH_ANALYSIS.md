# 검색 : Hash Table 선택 이유와 시간복잡도 분석

담당: 검색(`src/search.h`, `src/search.cpp`), 테스트(`tests/test_search.cpp`)

## 1. 한눈에 보기

| 기능 | 함수 | 자료구조 | 시간 | 추가 공간 |
|---|---|---|---|---|
| 인덱스 구축 | `buildSearchIndex(list)` | Hash Table 2개 (자치구 / 주차장명), Separate Chaining | O(n) | O(n) (참조 노드) |
| 자치구 검색 | `searchByDistrict(district, result)` | 자치구 Hash Table | 평균 O(1 + k) | O(k) (결과 복사) |
| 주차장명 검색 | `searchByName(name, result)` | 주차장명 Hash Table | 평균 O(1 + k) | O(k) (결과 복사) |
| 인덱스 해제 | `destroySearchIndex()` | - | O(n) | O(1) |

- n = 전체 주차장 수 (실제 데이터 842곳), k = 검색 결과 건수
- 조회 자체는 평균 O(1)이고, 찾은 k건을 결과 리스트로 복사하는 비용이 더해져 O(1 + k)이다.

## 2. 구조

### 해시 함수

- djb2 문자열 해시: `hash = hash * 33 + 문자`를 반복한 뒤 `% 211`.
- 버킷 수 211은 소수이다. 합성수보다 해시값이 고르게 퍼진다.

### 충돌 처리 : Separate Chaining

- 각 버킷은 `ParkingRefNode` 연결 리스트의 머리이다.
- 노드는 `key`(자치구 또는 주차장명), 원본 `ParkingNode*`, `next`를 가진다.
- 체인 끝에 추가하기 위해 버킷별 `tails[]`를 같이 둔다. 구축 시 체인 끝 삽입이 O(1)이고, 같은 key의 검색 결과가 **원본 리스트 순서**대로 나온다.
- 조회할 때는 버킷 하나의 체인을 따라가며 `key` 문자열을 비교한다. 해시값만 같은 **다른 key**(충돌)는 이 비교에서 걸러진다.

### 원본 참조와 결과 독립

- 인덱스는 `Parking` 데이터를 복사하지 않고 원본 `ParkingNode*`만 가리킨다. 인덱스 구축으로 늘어나는 메모리가 key 문자열과 노드 포인터 정도이다.
- 검색 결과는 `addParking()`으로 **별도의 `ParkingList`에 복사**해서 돌려준다. 호출자가 결과를 정렬하거나 수정해도 원본 리스트와 인덱스는 바뀌지 않는다.
- 검색 함수는 `result`에 남아 있던 값을 먼저 비운다. 결과가 없으면 `false`와 빈 리스트를 돌려준다.

## 3. 왜 Hash Table인가

이 프로그램의 검색은 모두 **"key가 정확히 일치하는 항목"** 을 찾는 것이다. (부분 일치, 범위 검색 없음)

| 방법 | 검색 | 구축 | 이 요구사항에서의 평가 |
|---|---|---|---|
| Linked List 순차 탐색 | O(n) | 없음 | 매 검색마다 전체를 훑는다. 이미 리스트가 있어 구현은 쉽다. |
| 정렬 + 이진 탐색 | O(log n + k) | O(n log n) | 연결 리스트는 중간 노드에 바로 갈 수 없어 이진 탐색이 불가능하다. 배열이 필요한데 STL(`vector`) 사용이 금지되어 있다. 자치구와 이름이 키 두 개라 정렬본도 두 개 필요하다. |
| 균형 BST (AVL 등) | O(log n + k) | O(n log n) | 구현이 복잡하고, 정확 일치만 필요한 이 요구사항에는 범위 검색 같은 장점이 쓰이지 않는다. |
| **Hash Table** | **평균 O(1 + k)** | **O(n)** | 정확 일치에 가장 적합하다. 구축이 한 번의 순회로 끝나고 구현도 단순하다. |

선택 이유 요약:

1. 정확 일치 검색만 필요하므로 순서 유지 기능이 필요 없다.
2. 평균 O(1) 조회로 검색 때마다 전체 탐색을 하지 않는다.
3. 연결 리스트와 배열을 직접 구현하는 제약 안에서 가장 간단하게 만들 수 있다. 버킷 배열은 고정 크기이고 체인은 `ParkingRefNode`로 만든다.
4. 자치구용과 주차장명용을 같은 `HashTable` 구조로 재사용한다.

## 4. 시간복잡도

### 조회

- 해시 계산: key 길이 L에 비례, O(L). 자치구/이름은 짧아 상수로 본다.
- 체인 탐색: 평균 길이는 **적재율 α = (서로 다른 key 수) / 버킷 수**. 해시가 고르다면 평균 O(1 + α)이다.
- 일치 항목 복사: k건이면 O(k).
- 합계: **평균 O(1 + α + k)**. α가 상수로 유지되는 한 O(1 + k).

### 최악의 경우

- 서로 다른 key가 모두 한 버킷에 몰리면 체인 길이가 n이 되어 조회가 **O(n)** 으로 떨어진다. (Linked List 순차 탐색과 같다.)
- 같은 key가 많은 경우는 다르다. 한 자치구에 주차장이 몰려 있어도 key는 하나이므로 체인이 길어지는 것이 아니라 **결과 건수 k가 커질 뿐**이다. 이 비용은 어떤 방법을 써도 결과를 복사하는 만큼 필요하다.

### 구축과 해제

- 구축: 원본을 한 번 순회하며 자치구용, 이름용에 각각 한 노드씩 O(1)로 추가. **O(n)**.
- 해제: 모든 참조 노드를 순회하며 `delete`. **O(n)**.

### 공간

- 참조 노드 최대 2n개 + 버킷 배열 2 x 211 x 2개 포인터(`buckets`, `tails`). **O(n)**.
- 자치구나 주차장명이 **빈 문자열**인 레코드는 해당 key의 색인에서 제외되므로 노드 수가 정확히 2n이 아닐 수 있다. 이런 레코드는 그 key로 검색되지 않고, `searchByDistrict("")`와 `searchByName("")`은 항상 `false`이다.

## 5. 실제 데이터 측정 (`data/parking.csv`, n = 842)

버킷 211개 기준으로 key를 버킷에 배치해 본 결과이다.

| 항목 | 서로 다른 key 수 | 사용 버킷 | 평균 체인 길이 (α) | 가장 긴 체인 (서로 다른 key) | key 하나의 최대 건수 |
|---|---|---|---|---|---|
| 자치구 | 25 | 24 / 211 | 0.12 | 2 | 79 |
| 주차장명 | 806 | 207 / 211 | 3.82 | 9 | 9 |

- 자치구는 key가 25개뿐이라 충돌이 거의 없다. 지배적인 비용은 조회가 아니라 결과 복사(최대 79건)이다.
- 주차장명은 key가 버킷 수보다 많아 평균 3.8개씩 체인에 쌓인다. 그래도 가장 긴 체인이 9라서, 조회 한 번에 최대 9번의 문자열 비교로 끝난다. 해시 분포가 한쪽으로 쏠리지 않는다.

조회 시간 비교 (주차장명, 리스트 끝에 있는 이름을 20000번 반복 검색, `-O2`):

| 방법 | 1회 평균 |
|---|---|
| Hash Table `searchByName` | 약 0.10 us |
| 리스트 순차 탐색 (같은 결과 복사 포함) | 약 3.9 us |

- n = 842에서 약 38배 빠르다. 순차 탐색은 n에 비례해 느려지지만 Hash Table은 α가 일정하면 거의 그대로이다.
- 측정값은 실행 환경에 따라 달라진다. 비율의 경향만 참고한다.

## 6. 한계와 개선 방향

- 버킷 수가 211로 **고정**이다. 데이터가 크게 늘면 α가 커져 조회가 느려진다. 그때는 버킷 수를 늘리거나 적재율이 임계치를 넘을 때 rehash(테이블 확장)를 하면 된다. 현재 데이터 842곳 규모에서는 불필요하다.
- 정확 일치만 지원한다. 부분 일치(`"노원"` -> `"노원구"`)나 접두사 검색이 필요해지면 Trie 같은 다른 구조가 맞다.
- 인덱스는 `buildSearchIndex()` 시점의 원본을 가리킨다. 원본 리스트를 정렬하거나 해제하면 참조가 달라질 수 있으니, 원본 변경 뒤에는 `buildSearchIndex()`를 다시 호출해야 한다. (`buildSearchIndex()`는 먼저 기존 인덱스를 해제한다.)
- 전역 Hash Table 2개를 쓰므로 인덱스는 한 번에 하나만 유지된다.

## 7. 테스트로 확인한 동작 (`tests/test_search.cpp`)

| 항목 | 확인 내용 |
|---|---|
| 빈 리스트 / `nullptr` | 비정상 종료 없이 `false`, 빈 결과 |
| 동일 key 집중 | 한 자치구 500건이 원본 순서대로 반환 |
| 해시 충돌 | 서로 다른 key 1000개(> 버킷 211개)를 넣어도 각 key가 자기 결과만 반환 |
| 없는 key / 부분 일치 / 빈 문자열 | `false` + 빈 결과 (이전 결과도 비워짐) |
| 결과 독립성 | 결과를 수정해도 원본과 인덱스가 그대로 |
| 안전성 | `result == nullptr`, 인덱스 해제 후 호출, 중복 해제 |
| 빈 key | 빈 이름/자치구 레코드는 색인 제외, `""` 검색은 `false` |
| 없는 key 충돌 | 사용 중인 버킷에 들어가는 없는 key 1000개가 모두 `false` + 빈 결과 |
| 메모리 | AddressSanitizer / UBSan / LeakSanitizer 통과 |

### 실행 방법

```bash
# 기본 실행
g++ -std=c++11 -Isrc tests/test_search.cpp src/parking_list.cpp src/search.cpp -o run_test_search
./run_test_search

# 메모리 오류 / 누수 / 미정의 동작 검사 (AddressSanitizer + UBSan, 누수는 LeakSanitizer가 함께 검사)
g++ -std=c++11 -g -fsanitize=address,undefined -Isrc tests/test_search.cpp src/parking_list.cpp src/search.cpp -o run_test_search_asan
./run_test_search_asan
```

누수나 잘못된 메모리 접근이 있으면 두 번째 실행이 오류를 출력하고 비정상 종료한다.
